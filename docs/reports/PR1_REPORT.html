重要配置逐项说明

"配置"就是程序运行前要告诉它的设置。PR1 只有 4 个运行设置，所有任务共用。每一项在任务真正动手之前都会被检查，填错就停下并给出说明。

运行设置（可用环境变量或本机 .env 文件覆盖）
DATA_ROOT必须填写，没有默认值
它是什么
所有数据的总文件夹，例如 /Volumes/DataDisk/pm-data。下面的 bronze、silver、gold 等子文件夹都从它派生，代码里不写死任何数据路径。
怎么检查
必须是绝对路径，不能含空字符。写任务前还会检查：能否真的写入、硬盘支不支持"硬链接"（安全发布文件要用到）；在 Mac 上如果放在 /Volumes/某个盘，这个盘必须真的插着，不能只是同名空文件夹。
为什么重要
外接硬盘没插好时，程序可能把数据写进电脑本地的同名空文件夹，数据就"丢"在错的地方。现在这种情况会在写入前被拒绝。
代码位置
src/config/models/pipeline.py
DATA_MIN_FREE_GIB默认 200（在 storage.json）
它是什么
写数据前硬盘至少要剩多少空间，单位 GiB。
怎么检查
只接受普通非负整数，4_000、+4、true 都会被拒绝。空间不够时，写任务在开始前停下，并说明还剩多少、要求多少。
为什么是 200
旧的历史归档约 36 GiB，解压、整理、重写还要几倍空间；与其写到一半撑满硬盘，不如开始前就拦住。
注意
只读任务和 check 命令不检查空间，也不创建任何文件夹。
PIPELINE_LOG_LEVEL默认 INFO（在 runtime.json）
它是什么
日志写多详细：DEBUG、INFO、WARNING、ERROR、CRITICAL 之一，大小写不敏感。
日志格式
每行一个 JSON，包含时间（UTC）、级别、事件名和消息，方便检索和排查。
注意
启动时的"配置记录"按 INFO 级别输出，设成 WARNING 以上就看不到；首个数据任务（PR2）要决定这条记录是否不受级别限制。
PIPELINE_CONFIG_DIR默认 src/config/defaults
它是什么
存放默认值文件（storage.json、runtime.json）的文件夹。默认值放在受版本控制的文件里，谁改过都有记录。
优先顺序
程序参数 > 进程环境变量 > 本机 .env > 默认 JSON。
围绕配置的几条机制
.env 文件每台机器一份，不进 Git
它是什么
本机的全局设置和密钥（例如以后用的 Kalshi、Polymarket API 密钥，PR1 还没用到）。任务参数不放这里。
怎么检查
文件不存在可以跳过；但如果它是文件夹、坏掉的快捷方式或读不了，就报错，而不是悄悄忽略。重复的键也报错。
配置报错信息src/config/validation.py
它是什么
配置填错时给出的说明文字。
设计
只使用一张事先审过的固定文字表，最多说出是哪个配置项错了，从不复述你填的内容。因为填错的内容可能恰好是密码。
启动配置记录事件名 config.effective
它是什么
运行 check 时输出一条日志：每个设置的实际值、来自哪里（如 environment:DATA_ROOT、default:storage.json），以及这些值的 SHA-256 指纹。
为什么
项目硬规则 10：任务开始时要能说清"这次到底用了什么设置"。指纹只看值不看来源，所以两次运行设置相同，指纹就相同。
边界
这 4 个设置都不是密钥，所以全部输出；.env 里的其他变量不会出现。写进运行记录数据库属于 PR2。
写入与数据规则里的固定设计
设计项具体是什么作用
写入角色6 个：imports、bronze、silver、gold、quarantine、manifests每个写入程序只能写自己那一层，写错层直接拒绝。
recovery 文件夹冲突文件和写到一半的文件放这里，每个附一份说明（原因、校验和、时间）出问题时保留证据，不覆盖、不删除。
写锁 .writer.lock同一时间只允许一个写入方；被占用时立刻失败，不等待防止两个程序同时写同一份数据。等待超时留到 PR2。
接收编号 receipt_id只能用小写字母、数字、_、-，必须是文件所在文件夹名区分两次独立接收；避免 Mac 上大小写不敏感导致 A 和 a 撞成同一个文件。
契约版本7.0.0数据规则每改一次就升版本；目前没有旧版本数据的迁移。
数字精度28 位，小数 10 位超出直接拒绝，不偷偷四舍五入。
价格与时间0–1，UTC价格就是概率；所有时间用世界标准时间。
交易所适配器声明9 项：能力、主键、分页方式、限速、时间含义、精度、交易所、API 版本、协议版本新增交易所时必须先声明这些，声明不合理就无法创建。

第一次独立验证：要求修改

2026-11-11修复后 320 项

三位验证者找出 9 类问题，例如：大小写不敏感的硬盘上 A 和 a 撞成同一个文件；recovery 说明文件损坏也被当成正常；配置报错的完整堆栈里能看到输入内容。这些问题之后按新流程分块修复（B1–B4）。

配置报错不泄露输入

B13 轮 + 负责人决定 + 2 轮
之前直接使用 pydantic 自带的报错文字，里面可能带着你填的字段名、字典键或取值。
之后只用固定的安全文字表，只报出已声明的配置项名；原始错误不挂在异常链上。
为什么：第 3 轮又发现一种内置错误会带出输入值，说明"逐个打补丁"不可靠，负责人决定改为固定文字。

文件：src/config/validation.py、loader.py、两份 config README

证据：针对未知字段名、字典键、类型标签三种泄露都有回归测试，检查完整堆栈不含输入。

写入层的持久性和恢复

B22 轮
之前新建文件夹后"落盘确认"失败，重试时因为文件夹已存在就跳过确认，可能误报写入成功。
之后不论文件夹是新建还是已存在，都确认其上级落盘后再发布文件。
之前中断残留文件的说明可以被改成"完整"，修改时间可缺失。
之后残留文件的说明必须写明"完整性未知"和带时区的修改时间，否则初始化报错且不动证据。

文件：src/data_io/layout.py

证据：模拟连续两次落盘失败，确认文件不会被发布；四种说明损坏都被拒绝并保留数据。

适配器出错时保留证据

B32 轮 + 负责人决定 + 3 轮
之前记录里有只读映射、超深 JSON、数字和文字混合的字段名时，程序直接崩溃，拿不到证据。
之后这些都转成统一的"规范化错误"，并带上原始记录。
之前默认任何 Python 对象都能复制，复制失败就丢证据；自定义对象还能在"复制"时偷偷把来源编号改掉。
之后只复制可信的内置类型；复制不了时保留原对象并标明"不是独立副本"。适配器只能拿到只读副本，改不了来源。
为什么：任意对象不一定能复制，负责人决定"能复制就给独立副本，不能就给原对象并明确标记"。

文件：src/adapters/base.py、src/data_schema/contracts.py

证据：伪造来源编号、自定义复制、不可复制对象等测试，成交和盘口两条路径都覆盖。

数据规则补漏

B42 轮 · 版本 3.0.0 → 4.0.0 · 408 项
之前覆盖率为 0 的分钟数据仍可填盘口值；一秒数据的中间价可以和买卖价对不上。
之后覆盖为 0 时相关值必须为空；中间价、微价格、不平衡度都要求两侧数据存在且自洽。
之前盘口里的价格和数量可以超出约定精度；当日成交笔数为 0 却有成交量也能通过。
之后超精度直接拒绝；成交笔数为 0 时成交量只能是 0 或未知。
之前价差计算受调用方小数精度设置影响；规则文件里重复的键会被悄悄覆盖。
之后价差用精确分数比较；规则文件出现重复键直接拒绝加载。
负责人决定：一秒数据里成交量未知时可以留空，盘口记录照样保留。

文件：schema_registry.json、contracts.py、docs/SCHEMAS.md

原始数据的来源和内容

B52 轮 · 版本 → 5.0.0 · 436 项
之前原始记录必须有交易所和 API 版本，内容必须是 JSON。
之后交易所、API 版本可以为空（不编造）；内容可以是 JSON 文本或原始字节，二者只能填一个。
之前先解析内容，再判断是不是送错了适配器。
之后先判断是否送错，再查时间、再解析；"写入时间早于接收时间"的记录保留，但不进入规范层。
为什么：送错地方的 CSV 字节会被误记成"本数据集损坏"，掩盖真正的调度错误。

文件：schema_registry.json、contracts.py、src/adapters/base.py

市场、选项、结算字段

B62 轮 · 版本 → 6.0.0 · 442 项
之前市场只有 open_at、close_at，分不清是计划时间还是实际时间；没有描述和结算条件。
之后拆成计划开放/关闭、实际开放/关闭四个时间；来源没说清时原文存进单独字段，不猜含义；新增描述和结算条件。
负责人决定：说不清的时间在规范层保留原文（我第一版只留在原始层，审查指出这是我自己的解读）。
