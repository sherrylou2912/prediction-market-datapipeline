# PR1 基础规则与后续实现边界

本文记录项目负责人确认的基础设计，供 PR1 后续代码块及未来数据任务使用。项目总体权威文件是 [`agent/PROJECT.md`](../../agent/PROJECT.md)，配置结构以 [`src/config/developing.md`](../../src/config/developing.md) 为基线；数据契约和代码仍需在后续代码块中逐项对齐本文。

**状态：设计规则，不代表能力已实现。** 当前工作区已有配置、目录写入边界、数据契约和模拟 adapter 的部分实现；不能据此认定本文所有规则已经生效。PR1 不实现真实下载、真实 venue adapter、PostgreSQL 账本、完整隔离审核流程、分钟聚合、回测引擎或 HTML 看板。真实数据覆盖、API 细节、存储格式兼容性与吞吐量需要在对应工作中验证。

## 1. 目标与范围

数据用于离线研究，近期重点是以 1 分钟实际成交价格、成交量和部分盘口汇总研究 taker 策略；未来优先扩展逐笔成交和盘口数据。基础规则同时考虑链上数据、体育粉丝等外部数据，以及 NLP 生成数据。

先完整定义跨数据集规则；具体字段只在用途明确时确定。PR1 优先讨论 Bronze 原始记录、Silver 市场、Silver 成交和 1 分钟 Gold 研究数据；其他数据先描述用途和扩展原则，不为未来能力创建空模块。旧开源代码及已有新 pipeline 代码均需评估：标明可迁移候选、只可参考的思路及需要重写的部分，不因已有代码就认定它符合新规则。

## 2. 配置、规则和版本

- 保留负责人参与设计的 `src/config/` 结构。`PipelineConfig` 管理共享运行环境；未来任务专属参数归相应任务配置。`DATA_ROOT` 必须显式提供，数据路径从该根目录推导。通用 `check` 不检查剩余空间、不试写、不创建目录；只读和写入任务分别调用对应 preflight。
- 从正常环境加载时，进程环境变量优先于本机 `.env`，再优先于 JSON 默认值。显式传入 `environ`、但未指定 `env_file` 时，保留与本机 `.env` 隔离的行为。配置对象无论通过加载还是直接构造，都不得接受非法字段；直接构造的校验是后续工作，尚未声称已实现。
- 规则统一管理标识、版本和查询方式，各条规则只有一个明确事实来源。数据契约属于 `src/data_schema/`，任务配置和未来质量参数遵循 `src/config/`，venue 的映射和协议语义属于对应 adapter；不要求把所有内容塞进同一个文件。
- 数据契约、去重、质量、转换和实验规则按各自内容分别版本化。含义、类型或必填要求变化时明确升级相应契约；旧版本不能被悄悄改写。运行记录和实验记录列出实际使用的规则及版本。具体机器可读字段、规则索引及版本兼容策略由相关代码块确定。
- API key 等密钥只从环境读取，不进入配置对象、规则、日志、manifest、报告或记录。未来如需 secret manager，应先明确调整项目规则。

## 3. 数据分层、来源与身份

| 区域 | 职责 |
| --- | --- |
| `imports/` | 外部文件或历史归档的导入区域。 |
| `bronze/` | 保留收到的原始内容和来源、接收时间、运行标识等追溯信息。 |
| `silver/` | 按数据契约转换并验证后的统一数据。 |
| `gold/` | 面向明确研究或回测用途的数据产品。 |
| `quarantine/` | 问题记录或批次及其原因、处理状态和追溯线索。 |
| `manifests/` | 文件及数据版本的来源、校验和、质量和审计信息。 |

任务使用对应层的 scoped writer，防止误写其他区域；这是程序边界，不是操作系统权限隔离。Bronze 不限于 JSON：来源 JSON 消息可以用 JSONL 压缩保存，来源文件可以保留原文件并记录定位信息；具体来源需要保留完整响应字节还是解析后的记录及页级信息，须在该来源设计时确认。原始内容不能被静默改写；收到相同数据多次也保留每次原始接收证据。失败转换不能抹掉原始记录。

保存来源内市场 ID 和 venue；不同 venue 的相同 ID 不表示同一个市场。Polymarket 的市场、condition 和 outcome 标识可能用于不同接口，目录标识及映射需在相应 adapter 中核实，不凭名称合并跨平台市场。平台没有稳定记录 ID 时，识别方法和风险需由对应来源明确规定，不能猜测唯一键。

所有新增 venue 实现 `VenueAdapter`，在 adapter 中声明能力、版本、来源规则并负责来源格式到统一契约的转换。错误、确实没有记录和不支持能力必须明确区分；外部数据不强行伪装成 venue。接口具体形式在后续代码块确定。

一对一转换的 Silver 记录应能定位具体 Bronze 记录；聚合或衍生数据通过输入清单和运行记录追溯来源集合。路径中使用的来源标识须能安全映射回原始标识，不以易变的标题充当唯一身份。

市场资料保留来源提供的名称、描述、outcome 说明和结算条件。保留有意义的历史观察；区分观察到的状态与来源明确提供的实际变化时间，后者未知时不能用观察时间冒充。成交资料需说明市场和 outcome、价格、数量与单位、来源时间及身份；来源不提供的信息不能编造。

盘口快照与增量、链上区块和日志、外部辅助数据、NLP 结果均需保留来源和时间语义。生成结果记录输入标识、方法或模型版本、参数和生成时间；适用时记录提示词或其版本。生成内容的 Silver/Gold 位置由用途决定，不默认完全可复现。

## 4. 去重、质量与人工审核

未来下载或接收时检查一次重复，全部相关批次的数据处理时再独立检查一次，覆盖跨运行、跨文件的重复。实时流没有整体下载结束，需要在明确的处理范围或窗口内进行第二次检查。两次检查都应记录结果，不删除 Bronze 的重复接收证据。同一标识但内容不同可能是来源修正或异常，不能静默当作普通重复丢弃。

异常不能进入 Silver；保存原始证据，并在 `quarantine/` 记录原因和来源。合格记录默认可以继续进入 Silver：例如收到 100 条、其中 2 条异常时，98 条可先入 Silver，2 条进入隔离流程，运行及 manifest 应记录数量和部分完成状态，不能宣称数据完整。来源确实为空、读取失败和来源不支持某项能力必须能区分。

回测前的流程是读取数据、发现问题时人工审核并修复或批准 caveat、处理数据、入 Gold 前验证、入库，再回测。没有发现问题的批次不要求额外人工确认。验证包含契约、业务规则、合理性、重复、覆盖和来源一致性等适用检查；无法判断完整性时标记未知。处理或最终验证中新发现的问题返回人工审核，修复后重新验证，或经人工批准附 caveat 后继续；不能让新异常静默进入 Silver 或未经审核影响 Gold。

问题等级为严重、中等、轻微；规则可给出建议等级，但必须经人工认可，也可人工修改并留存历史。所有等级均可经人工批准为 `approved with caveat`，但不能因此把 98/100 变为完整 100/100。修正另存修正值、原因和原始记录关联，不覆盖 Bronze。重新验证通过后，由人工确认解决；待处理标记可移除，原始问题和审核历史保留。未来提供可调用的审核功能，以及看板中的查看、修正和批准入口；本 PR1 不实现这些功能。

回测默认提示相关问题并允许使用经审核批准的数据。报告简洁列出相关问题、等级、当时审核说明和可能影响；无法判断时写明影响尚不明确，不强制计算百分比。优先报告与所用市场和时间范围相关的问题；影响范围无法定位时保守提示。问题状态可编辑，历史不可覆盖；回测记录保留运行当时的状态。

## 5. 时间与数值

- 区分来源事件时间、系统接收或观察时间以及处理时间。来源没有提供实际事件或变化时间时保留未知；处理时间不能冒充事件时间。
- 标准化时间使用带时区的 UTC，原始时间表达保留在 Bronze。历史来源若缺少真实可用时间，可以经人工批准使用明确记录的假设；假设不是已验证事实。
- 回测默认 `information delay period` 为 1 分钟，可由实验修改。feature 必须满足 `可用时间 ≤ 决策时间 − delay`。例如 `10:00` 决策、1 分钟 delay，只能使用 `09:59` 及之前已可获得的信息；窗口结束不自动证明所有输入和结果当时已可用。
- 1 分钟窗口按 UTC 整分钟划分，包含开始、不包含结束。例如 `09:59:00` 的成交属于 `09:59–10:00`，不属于前一分钟。市场历史的最近一次观察不保证两次观察之间状态没有变化。
- 价格、数量和金额使用精确十进制。默认契约精度为 `decimal(28, 10)`；特殊数据集可依据明确的来源和契约要求选择其他精度。对计算结果，默认舍入为 half-even，并记录相应规则版本；来源原始值不能被静默舍入或截断。具体来源超出所选契约精度时明确报告，并按适用质量规则处理。
- 没有足够输入计算 VWAP 或盘口平均值时保存为空，不填零。只有确认无成交时才能把成交量表示为零；数据缺失不能冒充无成交。

## 6. 1 分钟 Gold 研究数据

第一份研究产品面向 Kalshi 和 Polymarket，共同字段按市场和 outcome 表达；来源没有提供的可选指标标记缺失，是否需人工审核由明确的质量规则决定。

成交汇总包括开盘、最高、最低和收盘成交价（OHLC）、成交份数、可可靠计算时的成交金额、成交笔数和 VWAP。成交量与成交金额分别标明单位。如果多笔成交时间相同且来源不能确认顺序，不能猜测第一笔或最后一笔；受影响的开盘或收盘价标为未知并记录原因。来源只提供一个 outcome 时，只有规则明确允许才推导其他 outcome，且标记为推导值。

盘口包括最佳买价、最佳卖价、价差、买卖两侧每档价格、挂单份数及挂单金额，以及前 N 档汇总；N 默认 5，可配置并记录。价格、份数和金额分别以档位序号为键的 dictionary 表达，买卖两侧分开。数量与金额含义和单位必须明确，不能把挂单量当作已成交量。

若完整盘口实际少于 N 档，汇总实际存在的档位；如果只是来源覆盖不足，不得声称市场实际只有这些档位。空档或未知档不能默认为零。

盘口使用按持续时间加权的分钟平均，而非简单平均每次更新。各档挂单金额先按该时刻价格与数量计算，再按时间加权；不能假定平均价格乘平均数量等于平均金额。分别记录买卖两侧实际观察档位数的时间加权平均和最少值。价差只使用买卖双方同时有可靠报价的时间计算，并记录共同覆盖时间。

例如一分钟只有 50 秒可靠盘口时，平均值只计算这 50 秒并记录覆盖情况；缺失的 10 秒不能填零。覆盖率阈值尚未确定；过旧、断流或缺失的具体识别方式需随来源和质量规则设计。买卖双方各自及共同的覆盖信息应可供回测判断；分钟记录可保留所需的少量数值覆盖列，详细问题放在独立记录。

确认无成交但有盘口的分钟仍保留，价格为空、成交量为零并保存盘口指标；数据缺失则不能称为无成交。既无成交又无可靠盘口时，缺失范围仍需记录。分钟平均盘口不是某一瞬间保证可成交的价格或数量；未来 taker 回测应记录成交模拟、手续费、滑点、延迟和数据粒度等假设。

## 7. Parquet、manifest 与数据生命周期

Gold 数据按 venue、市场、产品、文件版本和 UTC 日期组织。不同 venue、不同市场分文件；每个文件只包含一个 UTC 日期，同一市场的多个 outcome 可在一个文件中区分。路径仅示意，市场 ID 的安全编码与各来源映射待实现时核实：

```text
DATA_ROOT/gold/<venue>/<market_id>/market_1m/<data_version>/YYYYMMDD.parquet
```

一个数据版本有一份 manifest，记录市场、日期、文件位置和文件版本，关联来源、规则版本、质量问题及审计信息；文件的校验和、行数和范围等清单信息同样需要可追溯。manifest 标识数据版本与文件集合，问题记录保存可编辑的当前状态和历史；状态变化不要求改写 Parquet。数据修复或更新产生可区分的新数据版本，旧回测记录保留当时输入和问题状态。

新版本可通过 manifest 引用旧版本未变化的文件，不复制整套数据。变化的市场日期文件可生成新版本；若修改影响其他衍生结果，也需重新处理受影响范围。旧文件被仍需保留的 manifest 引用时，不能当作无用文件清理。manifest 实际索引、持久化及文件/账本一致性留给后续实现。

未来按数据类型制定保留和归档策略，监控容量并在接近限制时提示；不能假设历史盘口等原始数据可重新获取。定期清理先生成清单供负责人确认，说明范围、空间、原因、归档校验情况和对追溯/复现的影响；确认前不自动删除。归档和清理要留下记录，manifest 不能继续假装文件仍在原位置。

## 8. 运行与实验记录、恢复和看板

数据任务和研究实验都需要机器可读的 `record.json`；人可读的 `report.md` 默认生成，可通过参数关闭。JSON 仍要包含必要的状态、结果和失败信息。两类记录均包含运行标识、时间、代码版本、影响结果的非敏感配置、输入和实际规则版本；未提交代码需明确记录，未知信息不能编造。数据任务补充范围、输出和数量；实验补充问题、方法、数据版本、参数、结论及限制。

未来 PostgreSQL 作为运行、checkpoint 和 manifest 的账本；JSON 为可读取、可复现的运行记录，Markdown 为人可读报告，以 `run_id` 等标识关联。文件与账本的一致性、崩溃后的恢复由后续设计实现。checkpoint 只能在数据文件可靠写入、通过适用验证并登记 manifest 后前进；问题记录也须可靠保存。文件已写入但 checkpoint 未推进时，恢复流程须检查并处理，不能丢失数据或产生不受控重复。

未来采用一个本地服务配合 HTML 交互式看板，供选择 venue、市场、时间和指标。打开时不加载全部历史数据，按需读取所选范围和列，放大后再加载所需细节；汇总方式和缺失须清楚呈现。看板显示数据及规则版本、覆盖情况和相关 caveat。初期查看已入库历史数据，不要求实时刷新；可手动导出当前图表，不为每个 Parquet 文件自动生成静态图。大数据查询、嵌套 dictionary 的 Parquet 兼容性和性能都需要真实规模测试，不能仅凭设计保证。
